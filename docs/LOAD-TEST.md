# 临时压测数据

本工具仅在系统尚未正式使用时，向选定门店导入虚构业务资料。它不是生产数据库迁移，没有网站入口；不创建账户、成员或门店，不改变 Access、STAFF_ACCOUNTS、业务授权或数据库结构。

## 1. 通过 Cloudflare 网页启用

已有网站、门店和 GitHub → Workers Builds 连接时：

1. 打开 **Workers & Pages → hearing-care → Settings → Builds**。
2. 确认 Build command 仍为 `pnpm run build:cloudflare`，无需更改部署命令。
3. 在 **Build Variables and Secrets** 新增普通构建变量：名称 `LOAD_TEST_CUSTOMERS`，值 `10000`。这是构建变量，**不是** Worker 的运行时 Variables and Secrets；不要添加 STAFF_ACCOUNTS 或复制 Token 到这里。
4. 保存，重试最新 `main` 构建。已有构建令牌的 D1 Edit 权限也用于导入，不需要本机登录或新的资源。
5. 构建先检查项目并应用正常迁移，再自动导入，每批最多 1000 名客户；日志只显示数量和进度，不显示令牌、账户邮箱或 SQL。
6. 等日志出现“压测数据核验完成”，并确认构建、部署成功，再刷新网站开始测试。
7. **导入完成后删除 `LOAD_TEST_CUSTOMERS` 构建变量**，保存设置。已有数据会保留。未设置、空值或 `0` 时，导入器不读取数据库，也不连接 Cloudflare。

全新空库没有任何门店时，导入器会说明“尚无可导入门店”并继续正常部署。先登录网站建立门店，再重试 `main` 构建；它不会猜测账户身份或绕过网站创建成员。

只存在一家未删除、未弃管且有启用成员的门店时，自动选择该店。多家符合条件的门店时，**拒绝写入**：需同时设置构建变量 `LOAD_TEST_STORE_ID`。可以在 D1 数据库 **Console** 执行下面的只读查询，查看门店 ID 与名称，再准确选定测试门店：

```sql
SELECT id, name FROM stores
WHERE deleted_at IS NULL AND abandoned_at IS NULL
ORDER BY name;
```

如果显式指定的门店不存在、已删除、已弃管或没有启用成员，构建报错，不自动改选其他门店。每条插入 SQL 也会检查门店和关联客户/设备当前有效状态。

## 2. 数据内容和额度

`LOAD_TEST_CUSTOMERS=10000` 生成：

| 内容     |                                    数量 |
| -------- | --------------------------------------: |
| 客户     |                                   10000 |
| 验配记录 | 550（500 位客户，其中 50 位有历史设备） |
| 听力检查 |                                     100 |
| 随访     |                                     250 |
| 维修     |                                      50 |

客户姓名为 `压测客户000001` 至 `压测客户010000`，电话为 `TEST-C000001` 等，亲属电话为 `TEST-F000001` 等。所有地址、病史和业务结果都是虚构的；不使用随机真实手机号。包含不同服务阶段、耳侧、历史设备、保修日期、完成/未完成随访和维修状态。没有报告文件、真实身份或新的 R2 对象。

数据库按现有索引估算，这批数据约占 **96850 行写入**，不是只计算 10000 条客户记录。此数依据当前迁移链估算；实际以 D1 指标为准，其他项目及当天已有操作也使用全账户额度。

[D1 免费额度](https://developers.cloudflare.com/d1/platform/pricing/)为每天 100000 行写入、500 万行读取，索引也计入写入。达到限额后，该账户 D1 查询可能失败，直到 UTC 00:00（北京时间 08:00）重置。**不要在批量导入同时压力测试**。若日志提示限额，保留开关，等次日北京时间 08:00 后再重试 `main` 构建；不自动升级套餐或循环重试。

导入文件按批次原子执行，已成功批次保留。固定 ID 与逐批数量核验用于断点续传；重试只补缺失的记录，不覆盖手工修改或恢复软删除记录。完整批次直接跳过，避免再次写入大量索引。核验包含软删除记录，因此在测试删除、编辑后再次构建不会复活资料。若手工物理删除某些资料，而它的父记录已经软删除，补录会拒绝并报错；不要通过直接删除 SQL 打破数据关联。

导入本身可能短暂阻塞 D1 请求，之后不改变日常接口的分页、查询路径或 Server-Timing。数据已导入不等于高并发压力测试完成；读写限额、网络延迟、TTFB 与 Worker/D1 耗时需要分别观察。不要把接近配额时的失败当成单条业务查询性能问题。

工具支持整数 100–50000；`50000` 按当前分布约需 484250 行写入，免费版需跨多个重置周期导入。本次建议先采用 `10000`，没有自动改为付费。

## 3. 本地生成与清理

如需本地检查、用 D1 Console 执行 SQL 或在已登录的开发机导入，可生成独立文件：

```sh
pnpm seed:generate --store-id 实际门店ID --count 10000
```

仅在忽略目录 `work/load-test/` 生成分批 SQL、`verify.sql` 和 `cleanup.sql`，不连接数据库。测试日期默认 2026-10-01，可通过 `--date YYYY-MM-DD` 调整。每条 SQL 按 UTF-8 字节数限制在 D1 的 100 KB 以内，生成文件不混入正式迁移目录或 GitHub。

`cleanup.sql` 仅软删除该店、本次固定测试前缀的客户，使用原有 30 天回收站与定时清理机制；其他客户和门店不受影响。它不会直接删掉私有附件目录或跳过 R2 清理。执行前先删除构建开关，停下压测；大量软删除也会更新索引、消耗写入额度，可将语句按客户 ID 范围分批执行。不要整库清空、删除账户/成员或改写 `d1_migrations`。

代码入口：[数据生成](../scripts/load-test-data.mjs)、[构建导入](../scripts/seed-load-test.mjs)、[回归测试](../tests/load-test-seed.test.ts)。正常构建和自动测试都不会连接正式 D1；只有显式启用导入开关的 Cloudflare 生产构建或开发机手动运行 `seed:remote` 才会导入。
