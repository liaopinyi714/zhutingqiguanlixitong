# 账户、门店和线上运行维护

核对日期：2026-10-01。首次资源创建见 [网页部署](DEPLOYMENT-GUI.md)，本章供已经上线的实例使用。

## 1. 提供者如何开通账户（仅网站操作）

1. Cloudflare → Workers & Pages → 当前 Worker → Settings → Variables and Secrets，找到运行时 **STAFF_ACCOUNTS Secret**。
2. 从你自己的受保护名单副本取得完整现有 JSON（控制台不一定能显示已保存 Secret）。不要用只包含新人的 JSON 覆盖原有名单。
3. 添加一项，例如：

```json
[
  { "email": "owner@example.com", "name": "店主甲", "role": "店主" },
  { "email": "colleague@example.com", "name": "店主乙", "role": "店主" }
]
```

这仅是格式示例；用真实授权邮箱替换并保留完整现有记录。email 不可重复，name 1–60 字，role 为店主；名单最多 50 行且整个 UTF-8 Secret 不超过 5120 字节，实际容量可能先达到字节上限。

4. 保存/部署 Secret；它必须在 Worker **运行时**设置，不是 Builds 的 Build Variables。
5. Cloudflare One / Zero Trust → Access Applications → 保护此网站的应用 → Allow 策略，加入相同邮箱并启用 One-time PIN。
6. 让新用户用自己的邮箱验证码登录。如果没绑定门店，进入个人/账户页是正常结果。
7. 需要加入现有店：已有店主进入那家店 → 头像 → 账户管理 → 添加已有店主 → 输入已开通邮箱。账户本人随后刷新或在账户菜单选择门店。

新用户不需要 Cloudflare 管理账户。系统没有密码和注册；任何门店用户都不能创建登录账户，收费由你在系统外进行。

STAFF_ACCOUNTS 的 tenantId/storeName 可以同时省略。仅首次引导某初始门店时使用这两个字段；门店和成员以后保存在 D1。修改已有用户名单 name 不会覆盖网站已保存的姓名。不要为了门店更名改变 tenantId。

## 2. 用户如何管理门店

| 需求          | 网站操作与结果                                                  |
| ------------- | --------------------------------------------------------------- |
| 建立门店      | 账户管理 → 新建门店 → 填名称；创建成员关系，再切入门店          |
| 切换          | 账户菜单或账户管理选门店；当前标签页业务列表清空后重新读取      |
| 更名          | 当前门店行铅笔；保存 D1，之后不必修改 Cloudflare 变量           |
| 加同事        | 添加已有店主，仅已在后台授权的邮箱有效；不能改对方个人资料      |
| 更换头像/姓名 | 编辑自己的账户资料；不同门店使用同一份资料                      |
| 停用成员      | 当前门店成员行操作；只撤当前门店权限，不影响其别家门店/个人资料 |
| 自己退出      | 门店行退出；无其他门店时仍能登录个人页                          |
| 恢复加入      | 已退出门店区域恢复加入；30 天内且资格未被现有店主撤销           |
| 删除门店      | 切入该店 → 删除 → 输入完整门店名称；即使唯一门店也可删除        |
| 恢复删除门店  | 删除未满 30 天，原有效成员在已删除门店区域恢复，然后切入        |

同一门店店主权限相同，任何有效成员都能管理该店和资料；适合共同管理，不适合需要只读员工权限的客户。

在线状态由客户端心跳和最近活动估算，后端窗口为 150 秒。浏览器后台节流、断网或关闭后会延迟变成离线；不是精确即时登录列表，不能用于判定权限或人员考勤。

## 3. 提供者撤销账户

从 STAFF_ACCOUNTS 完整名单移除该邮箱并保存，再从 Access Allow 策略移除。账号 D1 历史资料保留，但已签发 JWT 也不能绕过每次请求的名单检查。只在网站停用成员仅影响一家门店，不能代替全系统撤权。

提供者撤销一个门店的最后有效成员，Cron 会标记 abandoned_at，无人管理满 30 天清理该店资料。主动退出最后成员则立即标记。此期间可通过合法恢复/重新添加处理，超过期限不能恢复。恢复窗口内也应避免无人店长期被忽略。

## 4. 日常维护

- 营业结束做成套 SQL/附件备份并核对 COMPLETE；员工名单、Access 配置单独受保护保存。脚本不自动备份，也不自动停写。
- 发布前备份并记录代码版本；发布后确认 Cloudflare Builds/Deployments 对应提交成功，再用虚构资料验证登录、切店、检索和文件权限。
- 查看 Workers 错误/CPU、D1 行读写/容量、R2 用量；全账户的其他项目也占共享免费额度。
- Trigger Events 中确认 `0 18 * * *`（UTC，北京时间 02:00）；清理失败或附件积压超过单次 500 个时可能延后。
- 旧 Excel/备份文件受门店本地权限管理，线上恢复期限不控制离线文件。

## 5. 故障定位

| 现象                   | 优先检查                                                              |
| ---------------------- | --------------------------------------------------------------------- |
| 收不到邮箱验证码       | Access Allow 邮箱、OTP 登录方式、垃圾邮箱；不先改应用权限             |
| 401/登录过期/返回 HTML | 保存未提交内容，再退出 Access 并重新登录；不要反复点击保存            |
| 503 员工配置错误       | 运行时 Secret 有效 JSON、5 KB、重复邮箱、旧角色和初始门店成对字段     |
| 登录后无门店           | 是否刚开通独立账户/主动退出/停用/门店删除；先检查关系，不伪造门店变量 |
| 当前门店 403           | 本标签页门店资格已撤销；从账户菜单重新选择可访问门店，不强行写入      |
| 409 页面版本/写入状态  | 刷新版本或状态后重新操作，先保留未保存内容；不自动重复提交            |
| no such table / 500    | 查看最新 Build 迁移结果、DB ID/绑定；禁止将 Demo SQL 填入正式库       |
| 413                    | JSON/报告大小；单份报告 10 MB                                         |
| 500 request_failed     | 看匹配路由、错误类型及 Cloudflare 错误指标；不加敏感请求值日志        |
| 文件 404               | 归属/客户或附件已删除、对象是否存在；使用成套备份，不开放 R2 排障     |
| 推送后旧界面           | 对应提交是否实际部署成功，入口刷新；Git 推送成功并非上线              |
| 清理失败               | 检查 Secret 配置、DB/R2 绑定和 Cron 调用错误，备份后排查文件目录关系  |
| D1/Worker 配额错误     | 查看账户 Metrics 与 [部署额度说明](DEPLOYMENT.md)，等待重置或评估升级 |

代码回退不回滚数据库和 R2。误删使用恢复期内界面恢复；过期或存储事故按 [备份恢复](BACKUP.md) 在新资源验证，不直接覆盖正在使用的库。

## 6. 第一长期版本更新

本次收尾加强了写入期间的范围检查、保存与刷新失败的区分，并减少核心导出的查询。没有新的 Cloudflare 变量或数据库迁移；第一长期版本维护约定见 [长期版本说明](STABLE-V1.md)。提示“操作已保存，但最新资料暂时无法加载”时，只需刷新或查询，勿重复录入。收到 409 时先核实成员资格、删除状态或门店名称，再决定如何处理。
