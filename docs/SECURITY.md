# 权限与安全维护

核对日期：2026-10-01。说明当前措施及边界，不代表外部安全认证或无漏洞保证。

## 1. 权限矩阵

| 行为                                          | 系统提供者后台                         | 已开通、无门店账户   | 当前门店有效店主      |
| --------------------------------------------- | -------------------------------------- | -------------------- | --------------------- |
| 开通/撤销全系统登录账户                       | Access 策略 + STAFF_ACCOUNTS           | 不可                 | 不可                  |
| 修改本人姓名/头像                             | 初始名由名单提供；已存资料不由名单覆盖 | 可                   | 可                    |
| 修改其他账户姓名/头像                         | 网站也不可                             | 不可                 | 不可                  |
| 创建门店、查询自己的门店                      | 非专用平台功能                         | 可                   | 可                    |
| 读写客户、设备、维修、随访、报告、导出        | 不因 Cloudflare 管理身份自动获应用权限 | 不可                 | 可，限当前门店        |
| 更名/删除当前门店、添加已有授权店主、成员启停 | 无专用网站后台                         | 不可                 | 可                    |
| 主动退出/恢复加入门店                         | 不适用                                 | 退出后资格有效可恢复 | 可退出，30 天内可恢复 |

同店成员均为店主，拥有相同门店管理能力；不存在隐含“最高店主”或只读员工。平台管理者的云端数据库/对象/Secret 权限另属 Cloudflare 管理层，应限制账户管理权限和启用 MFA。

## 2. 身份与范围

- Access JWT 验签并检查签发方、AUD、有效期、sub/email/iat/exp/type；不信任纯邮箱请求头。
- 每次请求检查提供者名单，数据库遗留 managed 行不能开通登录；旧前台/验配师配置仅兼容语法，不授予身份。
- 门店资格来自 store_memberships，与全局个人资料分离。Cookie 和 X-Hearing-Store 只选择范围，服务端再次验证。
- 账户/门店解析每次用一条 SQL 读取当前个人资料、成员和门店状态，未跨请求缓存权限。只在本次门店列表请求内复用认证读取的列表；退出/删除等写操作后重新读取剩余门店。首次引导不覆盖停用/退出墓碑，事务完成后复读资格。在线状态更新也在 SQL 执行时核对成员及门店。
- 生产业务写入必须显式带本页门店，跨标签页 Cookie 变化不能让保存到错误门店；显式无权范围不回退。
- 客户业务查询限制门店，子记录同时限制所属客户；设备维修引用同门店同客户有效设备。个人资料和本人门店列表按身份查询，不强制绑定门店。
- 无门店账户可以登录个人页，但业务/附件/导出接口统一拒绝。
- 客户业务 SQL 写入再次检查有效门店、当前成员、客户及关联设备；成员被停用、门店或父记录被删除的在途请求不能继续写入。零变更返回 409，不生成成功审计。门店添加成员、更名及删除也复核执行时资格；删除时再次匹配确认名称。

撤销权限会在后续请求生效，已完成的下载副本无法远程撤回；正在执行且已验证过的读取没有额外取消机制；业务写入仍受执行时 SQL 检查，但提供者名单变更不具备跨在途请求取消机制。页面刚显示的成员在线状态也不是授权依据。

## 3. HTTP、输入与文件

生产写请求同时验证同源 Origin 与自定义请求头，不开放业务 CORS。JWT 提供真实身份；自定义头只是来源防护的一部分。API 不缓存；错误日志仅记录匹配路由和错误种类，不输出 SQL 值、客户内容、令牌或文件名。

Zod 校验 JSON、参数化 SQL、固定表名白名单；请求体大小限制。静态资源 CSP、防嵌入和 nosniff 见 public/_headers，API 响应头由统一中间件设置，API _headers 不自动生效。

R2 桶不公开，下载必须经过身份/门店/有效客户/附件验证，强制 attachment。文件大小和 PDF/JPEG/PNG 格式头检查**不是病毒扫描**。头像拒绝外链/SVG，只允许有限小型 raster data URL。用户文本按 React 文本和 XLSX inlineStr 输出，Excel 中以 =/+/@ 开头的内容不作为公式执行。

Demo 必须 DEMO_MODE=true 且主机为 localhost、127.0.0.1、[::1]；公网即使误开开关也不能使用 Demo 登录。生产迁移和 R2 独立于演示。

## 4. 删除、配置和备份

恢复期限在执行 SQL 时重新验证，客户和维修设备关系有效才恢复。到期清理顺序及失败行为见 [数据模型](DATA-MODEL.md)。不公开“物理删除”接口。

STAFF_ACCOUNTS、构建 Token、rclone 凭证只存受保护配置。更新名单必须保留完整授权邮箱，误覆盖会撤销访问并可能使门店进入无人保留期。无效名单不会被当成空名单去新标记无人门店。

GitHub 不存客户资料；Excel、JSON、SQL 和报告下载均含敏感业务资料，门店负责限制离线文件的接触范围与保留期限。线上删除不会销毁旧备份，见 [备份](BACKUP.md)。不要把真实业务数据放入测试夹具、截图、Issue 或日志。

## 5. 当前没有的能力

没有独立 API Token、复杂角色/字段权限、专门限流服务、病毒扫描、不可篡改审计、自动异地备份、写入冲突版本和端到端加密。当前权限/隔离由参数化 SQL 和应用逻辑实现，D1 没有额外应用级行权限机制。

不应向未授权客户宣称“自动备份”“全平台账户管理”“并发编辑保护”等能力。多门店上线前核对各域名 Access 保护、名单、私有桶与备份安排；网络体验和数据所在地还需结合门店实际条件判断。

## 6. 发现异常时

暂停相关账户/门店写入，保留当前 SQL/文件和 Cloudflare 错误时间；通过后台 Secret 撤销可疑邮箱，并移除 Access 策略。不要在排障期间开放 R2、设置 Everyone/Bypass 或关闭 JWT 校验。使用虚构资料复现，按 [运行维护](OPERATIONS.md) 排查，再在隔离环境补回归测试后发布。
