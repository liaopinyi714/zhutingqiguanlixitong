# 数据加载、分页与 D1 查询

核对日期：2026-10-01。保持 Workers + D1 + 私有 R2、现有门店权限及业务结构。

## 1. 原来的全量读取位置

| 接口/调用方                         | 原来行为                           | 现在行为                                     |
| ----------------------------------- | ---------------------------------- | -------------------------------------------- |
| GET /customers                      | 整店客户，登录后及保存后重复加载   | 默认 50 条；独立单客查询，不靠第一页找到客户 |
| GET /devices、/repairs、/warranties | 整店验配/维修/保修记录             | 服务端筛选、搜索及游标分页                   |
| GET /followups                      | 全部随访，浏览器再筛选与计数       | 服务端筛选及分页；首页仅 4 条待办            |
| GET /customers/removed              | 全部恢复期内客户                   | 按删除时间分页，进入回收站才读取             |
| App 登录/refresh                    | 同时读取全部目录，保存后再次全读   | 根据所在页面读取，保存后刷新当前资源         |
| 首页/统计页                         | 浏览器对完整客户/设备/随访数组统计 | /summary 使用 D1 COUNT、SUM、GROUP BY        |
| 表单候选客户/设备                   | 依赖已下载的全部数组               | 30 条候选项，可搜索整店并翻页                |
| 重复客户提示                        | 浏览器检查整个客户数组             | 姓名、生日、门店联合索引查询，最多 5 条      |

## 2. 页面读取计划

`src/readPlan.ts`、`useWorkspaceData.ts` 管理主页面的读取需求；`ServiceDirectory.tsx` 自行请求对应目录。

- 首页：6 位最近客户、4 条未完成随访、基础统计摘要。
- 客户列表：当前筛选与关键词的一页客户、基础摘要。
- 客户详情：单客基本资料及其 detail/removed；不读取整店客户列表。
- 设备/维修/保修：对应目录一页、基础摘要；只有点击新增才读取表单候选项。
- 随访：当前筛选一页、基础摘要。
- 统计：基础聚合摘要；不下载客户、验配或随访原始列表。
- 回收站：一页恢复期内客户。
- 账户、设置、建档：不预读业务目录。打开搜索入口才读取最近客户；输入关键词仍请求整店 `/search`。

当前页、筛选或门店变化时清空旧页的展示和游标。资源键包含门店与查询路径，请求序号拒绝晚到响应；退出后取消旧结果应用。前端只保存当前页和用于返回的游标历史，不累计历页客户数据。筛选输入防抖 180 ms；骨架仍按真实区域加载状态显示，没有人为加载延迟。

保存后刷新当前资源；返回别的页面会重新按需查询。更新、删除和恢复不自动重复提交。分页失败可以重试；无效/跨日游标重试回到第一页。通知在无需摘要的页面沿用本门店此前已获得的小型摘要，不显示其他门店的缓存。

基础摘要在同一门店、同一日期的页面间复用，避免每次跳转都重新聚合；保存或北京时间日期变化会重新读取。日期检查只在浏览器本地执行，页面可见时每分钟检查或切回标签页时检查，并非每分钟查询 D1。

## 3. 游标契约与排序

六个列表接受 `paged=1`、`limit`、`cursor`、`filter`、`q`，返回 `{items,nextCursor}`。limit 默认 50、最大 100；使用 limit+1 判断还有下一页，不额外执行全表匹配数 COUNT。未带 paged=1 的旧调用仍返回数组，但同样有页大小上限，不存在绕开分页获取全部记录的参数。

| 列表   | 排序（最后一项为唯一 ID）                                                      |
| ------ | ------------------------------------------------------------------------------ |
| 客户   | created_at DESC、id DESC                                                       |
| 回收站 | deleted_at DESC、id DESC                                                       |
| 设备   | date DESC、created_at DESC、id DESC                                            |
| 维修   | 待送修优先、维修中其次、其余最后；occurred_date DESC、created_at DESC、id DESC |
| 随访   | completed ASC、due ASC、id ASC                                                 |
| 保修   | 保修日期 ASC、id ASC；未填日期置于末尾                                         |

游标编码版本、门店、接口、筛选、关键词及最后一条的排序值；不使用 OFFSET。随访、保修和回收站的游标另外包含北京时间日期，避免跨日继续使用旧的相对日期范围。普通列表不因午夜自动失效。游标是可读的位置标识，**不是凭证或权限**，其中不放客户姓名/电话；门店和查询参数仍由服务器独立验证并绑定 SQL。

普通列使用 SQLite 行值范围比较 `(排序列...,id)<或>(游标值...)`。SQLite 对行值内的表达式未必形成范围定位：维修优先级和保修日期分别查询“相同表达式值的剩余记录”和“后面的表达式值”。只有第一个区间不足 limit+1 才查询第二个，合计返回最多 limit+1 行；两个区间均使用索引范围和 LIMIT，不把大批结果拿到 Worker 排序。

筛选随访时，已在 WHERE 固定完成状态/今日日期的前导列从范围比较中移除，改为直接定位剩下的 due/id 或 id；避免固定前导列让 SQLite 仅查到该状态的索引开头。

上一页记录其起始游标，不支持任意跳到第几万页。新建记录不会挤入已翻过的后续页。删除边界行不影响继续定位；其他用户修改排序值/筛选条件后记录可能移动，分页不是跨请求数据库快照，需要重新加载第一页查看最新状态。

## 4. 权限、搜索与统计

所有读接口均在统一 HTTP 权限中间件之后注册；每次查询绑定已验证 tenant_id。设备/随访关联当前门店有效客户；维修还关联同门店、同客户的有效验配，删除父记录即隐藏子记录。独立单客查询和候选项使用同样的规则，外店/已删除客户返回 404，不根据分页游标授予访问。

列表关键词在 SQL WHERE 中应用，先筛选再 LIMIT，搜索全部门店数据。列表的 `%`、`_`、`!` 按普通字符转义；完整 LIKE 模式最多 50 UTF-8 字节。原有跨客户/检查/设备/维修/随访搜索保留，返回最多 50 位客户，范围始终是整店。

基础摘要计算客户服务阶段、已验配客户、待办/完成/今日/逾期、有效设备/维修数及到期保修数。已验配客户沿用既有阶段口径（已验配或长期随访）；保修提醒沿用已到期加未来 90 天。统计页保留可跳转查询的统计卡片和 Excel 导出，已移除没有明细入口的四个分布面板，因此不再请求详细摘要。内部接口仍兼容 detail=1，另按来源、当前年龄分组和随访类型聚合，只返回分组及数量。日期按北京时间，未填写生日单列；SQL 排除外店和已删除父/子记录。

## 5. 索引和实际成本

正式增量迁移是 `migrations-production/0008_paged_read_indexes.sql`；本地演示为 `migrations/0013_paged_read_indexes.sql`。新增有效记录的部分索引：客户页/阶段/统计/重复检查、回收站删除日期、设备页/耳侧/保修表达式、维修优先级/状态、随访完成状态与日期。保留已有客户、设备外键关联索引；维修数量只按当前页每台设备的关联索引计算。

分页测试通过 EXPLAIN QUERY PLAN 核对第一页、深游标及表达式后续区间使用索引，无 OFFSET 和大结果临时排序。测试是本地 SQLite 的执行计划验证，**不是 D1 实际 rows_read 数值**。

索引减少定位、排序和无关门店的扫描，不保证每页恰好只读取 51 行：父记录校验、维修数量和选择性低的搜索会产生额外读取。包含词语的 LIKE 通常不能直接由普通 B-tree 定位，仍可能扫描本门店候选行；精确 COUNT/GROUP BY 也需扫描相关索引记录。主要改善是减少重复全读、网络传输、浏览器计算和深页遍历，没有宣称聚合为常数成本。索引增加存储和写入成本，不为报告字节或无关自由文本创建索引。

上线后在 D1 Metrics/查询分析核对 rows read、rows written 和 Worker CPU；按实际查询与数据分布调整，不加入分片、额外数据库或永久统计缓存。参考 [D1 索引](https://developers.cloudflare.com/d1/best-practices/use-indexes/)、[D1 指标](https://developers.cloudflare.com/d1/observability/metrics-analytics/) 和 [SQLite 行值分页](https://www.sqlite.org/rowvalue.html)。

## 6. 保留的完整读取与发布

用户主动打开一个客户时，详情和该客户的恢复记录仍完整读取，支持听力历史比较、业务关联跳转和编辑恢复；它们不是整门店预加载。单个档案积累极多历史记录时可再单独设计分段读取。主动 JSON/Excel 导出与完整备份仍需要完整资料，属于明确的导出操作，不用于日常页面或统计。

既有 Workers Builds 使用 `pnpm run build:cloudflare`，会在发布前自动应用新索引迁移。无需新资源、变量或重新建库；核对该提交的迁移和部署成功。手动部署要先运行 `pnpm db:production`，再发布；本地演示运行 `pnpm db:local`。新增迁移不能改写已经执行的旧文件。完整操作见 [部署](DEPLOYMENT.md) 与 [网页部署](DEPLOYMENT-GUI.md)。
