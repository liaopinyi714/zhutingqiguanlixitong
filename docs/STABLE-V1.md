# 第一长期版本 · v1.0.0

整理日期：2026-10-01。版本号来自 package.json。本文件记录源码基线、维护约定和发布核对方式；线上实际版本以 Cloudflare 成功部署的 Git 提交为准。

## 1. 已确定的使用范围

面向助听器门店，管理客户、听力检查、历次验配、设备维修、随访预约、私有报告、保修提醒及离线 Excel 表格。没有库存、在线收费、公开注册或账号密码登录。

界面沿用已确认的简洁控制台风格。查询入口、页内编辑、关联跳转、移动端布局和按实际页面显示的渐进骨架属于本版本基线，维护时应保留。

账户由系统提供者通过 Cloudflare Access 策略及 STAFF_ACCOUNTS 开通。账户独立于门店，同店有效成员均为店主；只有这些成员能读写该店资料。删除和主动退出的恢复期均为 30 天。详细流程见 [账户与运行维护](OPERATIONS.md)。

## 2. 数据和权限保护

- 生产 JWT 校验、提供者名单及门店成员资格在服务端执行，不能用客户端角色或门店 ID 代替授权。
- 客户业务写入在 SQL 执行时再次检查门店、成员和有效客户；维修写入还检查关联设备。状态已变化则返回 409，不留下成功审计。
- 写入及对应审计使用同一 D1 batch。附件独立经过身份、门店和客户校验；上传后 D1 失败或资格变化时尝试删除已写入的 R2 对象。
- 列表只读取当前游标页，搜索范围仍为整个当前门店；统计由 D1 聚合。核心 Excel 仅查询客户和验配，业务 Excel 按需查询最新听力、维修和随访。
- 前端拒绝晚到的旧结果覆盖更新后的档案。服务器确认写入后关闭录入表单；刷新失败提示已保存，不自动重发写入。

这些措施不等于并发编辑版本控制：同一有效记录被两位店主修改时，后保存的内容仍可能覆盖先保存的内容。请求的写入响应丢失时也不能自动判定是否已保存，应先检索核实；本版本没有幂等键。

## 3. 发布前核对

1. 保存代码版本，按 [备份恢复](BACKUP.md) 完成 SQL、报告及受保护配置的备份；代码检查不会自动备份或暂停写入。
2. 在 Node.js 24.x / pnpm 11.19.0 执行 `pnpm install --frozen-lockfile`，然后运行 `pnpm check`、`git diff --check` 和 `pnpm exec wrangler deploy --dry-run --outdir .deploy-dry-run`。
3. 使用现有 main → Workers Builds 路径。构建先配置、检查、应用正式增量迁移，再发布；不要将演示迁移导入生产库。
4. 本次收尾没有新增迁移或环境变量；第一长期版本包含此前的正式迁移 0001–0008。已有构建会应用尚未执行的迁移，不需要重新建库。
5. 确认 Cloudflare 对应提交部署成功。随后使用虚构资料核对登录、切店、全店搜索、保存、关联维修、导出和私有附件下载，再清理验证记录。

Git 推送、自动测试、dry-run 和配置格式检查，都不能独立证明生产域名的 Access 策略、绑定资源或实际部署正确。测试使用内存 SQLite、模拟 R2 和身份，不读写真实客户资料。

## 4. 维护规则

- v1.0.x 用于兼容性修复；新增业务能力再考虑次版本。每次修改提交代码、必要回归测试及 CHANGELOG，不改写已执行的数据库迁移。
- 不自动重发写入，不把刷新失败提示成保存失败。新增写路由必须沿用 HTTP 边界、SQL 范围验证、事务审计与失败状态码。
- 附件路由必须挂在 HTTP 边界和有效客户中间件之后。保持桶私有，不将文件处理改为公开链接。
- 数据库/R2 的变更和代码回退分别处理；回退代码不会回滚迁移或恢复已清理文件。
- 不为整理目录改变数据模型、引入单位层级、收费系统或数据库分片。调整索引时先核对实际 D1 指标及查询计划。
- 依赖升级单独检查锁文件和回归。不要为追求新版本，在营业使用期间同时更换框架、认证和存储。

## 5. 仍需日常维护的边界

每日 Cron 清理、人工成套备份、Access/名单维护和额度监测仍需要提供者负责。LIKE 包含搜索和精确聚合有扫描成本；单客历史及主动导出仍可能读取较多数据。数据所在地、中国大陆连接体验和云服务费用需按实际使用核对。

没有自动异地备份、编辑冲突提示、病毒扫描、不可篡改审计或外部 API Key。完整边界见 [安全说明](SECURITY.md)、[数据加载](DATA-LOADING.md) 和 [开发维护](DEVELOPMENT.md)。
